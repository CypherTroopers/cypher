# Fresh-genesis cutover plan — NOT EXECUTED

Do not run the existing root `init.sh` automatically. It deletes broad sets of data and stops **ALL pm2 processes**. Existing live processes use `chaindb0` through `chaindb6` and `chaindbmine`; this implementation has not stopped, restarted, opened those chain databases, or deleted them.

This plan is for the earlier v3-to-v4 genesis/relay cutover. The TxQUIC automatic-role correction uses the existing `miner.start` identity and does not itself require a reset, new datadirs, or new committee identity configuration files.

1. Review the uncommitted implementation, test logs, unique `/tmp` candidate binary and configuration templates. The relay is an opt-in FHS-D feature; upgrade all participating gateways/common nodes and validators together. The PoW transport v2 and corrected seal commitment require a fresh network genesis.
2. Independently record current process IDs, exact commands, configuration, datadir ownership and chain/genesis hashes. Back up wallets, keystores, BLS identities, public enode pins, genesis, configuration and all databases using an operator-approved consistent backup procedure. Do not print secrets into logs.
3. Prepare **new paths** for each future node datadir and its operator config. Preserve existing `chaindb0..6` and `chaindbmine` and their outboxes. Never copy a v3 chain database into the new v4 network. Pending old-network signed transactions/admissions are not automatically valid on the new genesis.
4. Review the shipped genesis's new mixHash commitment. No committee, allocation or other genesis field was changed. If an operator changes committee endpoints/keys or other committed config, recalculate the commitment consistently before initialization. Ensure every new node uses byte-identical reviewed genesis and the same fresh hash. The expected mixHash for the currently supplied config is documented in architecture.md; mixHash is not the full genesis block hash.
5. Replace every TEST-NET example enode with an explicit operator-owned identity. Committee nodes pin their core peers; common nodes use bounded diverse common peers. Only selected gateway configs set Relay.Gateway. Keep TxQUIC.AutoRole enabled and use the existing miner.start BLS key-loading procedure: verified membership in the current canonical committee activates ingress. No TxQUIC.CommitteePublicKey hint is required. Keep existing BLS private key handling separate from public P2P pins.
6. In a separately authorized maintenance window, stop **only the specifically approved named processes**, initialize only the newly prepared empty datadirs with the reviewed genesis and candidate binary, and start only the approved new instances. This document deliberately does not provide or execute a broad cleanup command. Do not overwrite existing binaries.
7. Before accepting traffic, verify canonical genesis agreement, reserved core reconnection under public pressure, validated block/keyblock sync, two reachable gateway paths per neighborhood, n-f durable transaction receipts, full committee PoW admission receipts, unchanged reward identities, bounded queues/bytes, and fail-closed behavior with gateways unavailable.
8. Run a separately planned 300–400-process experiment with resource, throughput, latency, churn and malicious frame measurements. Account explicitly for the residual shared 257 MiB RLPx frame allocation exposure; relay payload caps alone do not establish a process memory ceiling. Current tests are loopback application tests and an admission simulation.

Rollback is an operator action using preserved binaries, configurations and original datadirs under a separately approved process plan. Do not point an old binary at the new v4 data or a new binary at the live v3 databases.
